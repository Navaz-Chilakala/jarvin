# Jarvin full-product build order

Updated 6 November 2026. This plan starts from [product status](PRODUCT-STATUS.md), not from an assumed finished assistant. The target is an English-first, local-first Windows companion that stays active while its main window is hidden, listens without a wake phrase, can be interrupted while speaking, observes the visible desktop, and uses the actual mouse and keyboard to finish user-requested work. Phone control remains deferred.

## Architecture decisions

- **Screen capture is continuous; model inference is selective.** Keep the latest frame available to the agent, but run the local vision model when a command, relevant screen change or action needs interpretation. Feeding every captured frame to the 4B vision model would consume latency and GPU memory without ensuring faster action. This is an engineering choice to measure on the target laptop.
- **One capture/input boundary.** Route every screen image and input action through the same display/window policy and audit record. The existing Electron `desktopCapturer` path uses a source `display_id` that matches Electron's display ID. A native capture adapter can replace its frame source without changing agent tools. [Electron source documentation](https://www.electronjs.org/docs/latest/api/structures/desktop-capturer-source).
- **Windows capture backend.** Windows.Graphics.Capture supplies display/window frames through a frame pool. DXGI Desktop Duplication is a candidate if dirty/move regions or cursor metadata prove useful for frame processing. Choose with measured latency and stability, not by API name alone. [Windows.Graphics.Capture](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture), [DXGI Desktop Duplication](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api).
- **Input boundary.** Continue using foreground checks and Windows `SendInput`; it is limited by Windows integrity levels, so elevated windows, UAC and the secure desktop are outside ordinary control. [Microsoft SendInput documentation](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput).
- **Extensibility follows task reliability.** Keep the existing MCP, skills and local memory foundation. Add RAG for a real document corpus and managed connectors for selected workflows. Defer A2A, A2UI, payment protocols, agent registries and knowledge graphs until a concrete workflow needs them.

## Immediate implementation slice

1. Harden the new per-app/window exclusions before a live frame service is enabled. Privacy settings now accept process names and title phrases, offer an open-window picker, filter excluded windows from Jarvin's list, and block whole-screen capture while an excluded window is visible. The persistent **Pause observation** control blocks built-in captures. The exclusion scanner and input guard need real-app acceptance; external MCP servers and shell commands need separate policy enforcement.
2. Introduce a `FrameProvider` interface behind the existing screen observer and implement a selected-display Windows.Graphics.Capture provider with the Electron provider as fallback. Keep only recent frames in memory unless the user explicitly saves a screenshot.
3. Feed timestamped frames to the existing visual grounding loop; show when the frame is stale, and recapture after focus, click, typing, scrolling or display changes.
4. In parallel with the capture work, instrument the voice pipeline so a physical-microphone session can identify whether capture, speech detection, recognition, model response or speech output causes delay.

The user requested no test runs during the current build work. Build and static checks may continue; live acceptance and latency measurements remain pending until that instruction changes.
