# Voice and desktop control research

Reviewed 6 November 2026 for Jarvin's local Windows voice and desktop workflow. Repository feature claims are not independent acceptance results.

## Candidate projects

- [Wheelhouse](https://github.com/wheelhouse-project/Wheelhouse) (Apache-2.0) provides local voice control, dictation, named/numbered controls and focused-text checks. Its [scroll action tests](https://github.com/wheelhouse-project/Wheelhouse/blob/main/services/wheelhouse/tests/test_scroll_action.py) show spoken counts and explicit zero handling. Jarvin independently implements a small count parser (zero through ten), routes scrolling to the foreground app when Jarvin is unfocused, and keeps explicit chat scrolling. No Wheelhouse code is copied. The full project is Python-based and would need architectural review before adopting it or its components.
- [Windows Computer Use](https://github.com/cgissing/windows-computer-use) (MIT) offers a Node/PowerShell MCP server with Windows UI Automation, screenshots and mouse/keyboard operations, including drag and double-click. Jarvin already has a Windows worker and MCP client; evaluate individual capabilities and permission behavior before adding another desktop-control server. It has not been installed or tested in Jarvin.
- [agent-windows](https://github.com/XiaofengdiZhu/agent-windows) (MIT, with separately licensed vendored components) combines screenshots, UI Automation and visual grounding. Its repository says it is abandoned. Consider its documented observation patterns as research; do not treat it as a maintained dependency.

## Silero comparison tool

`npm run check:vad-compare -- scratchpad/silero-vad-v6.2.onnx path/to/recording.wav` runs the existing amplitude segmenter and Silero locally on the same 16 kHz mono WAV, up to two minutes per file. It reports detection counts and timing without changing Jarvin's live listener or recording new audio. Counts alone are not accuracy; use clips labeled for speech and ambient noise and compare against those labels. This harness is an independent adapter to the existing `sherpa-onnx-node` runtime; it does not copy Silero source code.

The model is now bundled in `assets/voice` with its MIT license notice: upstream [Silero VAD v6.2 model](https://github.com/snakers4/silero-vad/tree/v6.2), SHA-256 `1a153a22f4509e292a94e67d6f9b85e8deb25b4988682b7e174c65279d8788e3`. The automatic Qwen3-ASR path first segments by microphone level, then checks the finished clip with Silero in the isolated native worker before decoding. Manual microphone checks bypass Silero so they still display the raw recognizer output. If the detector cannot load, Qwen falls back to the amplitude path. This integration has not been tested on the user's microphone; false rejections and added latency still need measurement.

On a generated 6.12-second clip with 1.5 seconds of leading silence, both detectors reported one speech start and one completed segment; a three-second silent clip produced no starts. These are smoke checks, not an accuracy benchmark. The listener's initial noise calibration has since been shortened from one second to about 0.4 seconds. A clip that begins immediately can still be missed during that interval; real recordings should include the same startup conditions as the live listener.

The detector uses the already installed `sherpa-onnx-node` wrapper; no Silero source code is copied. Preserve the model license notice when packaging or redistributing Jarvin.

## TeamViewer comparison for Windows control

[TeamViewer's remote-control explanation](https://www.teamviewer.com/en-us/solutions/use-cases/remote-control/) describes a live screen stream paired with mouse commands and keyboard input. Its [session toolbar documentation](https://www.teamviewer.com/en-us/global/support/knowledge-base/teamviewer-remote/remote-control/remote-session-toolbar/) describes direct keyboard mode and monitor selection. This describes remote human control, not an AI that understands a screen. Jarvin runs locally and uses individual screen images, a vision model to locate a requested target, actual Windows pointer/keyboard input, and a fresh image to assess the result. The new `visual_type` action keeps the target bound to one foreground window while clicking and typing; it does not submit a form.

TeamViewer's [UAC instructions](https://www.teamviewer.com/en-us/global/support/knowledge-base/teamviewer-remote/remote-control/control-uac-during-a-teamviewer-session/) say an ordinary session cannot control elevated prompts without an administrator-authenticated setup. Microsoft's [SendInput documentation](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput) likewise limits input injection across Windows integrity levels. Jarvin does not claim control of UAC, the secure desktop, locked sessions or higher-integrity apps. Jarvin can now select a display and map its image to physical monitor coordinates, including negative origins; mixed-DPI layouts, application focus, text entry and unexpected popups still need physical Windows acceptance work. No TeamViewer code is used.

## Established technical path

There is no single Windows or agent protocol that makes natural-language computer use reliable. The parts with mature specifications are [Windows.Graphics.Capture](https://learn.microsoft.com/en-us/windows/apps/develop/media-authoring-processing/screen-capture) or [DXGI Desktop Duplication](https://learn.microsoft.com/en-us/windows/win32/direct3ddxgi/desktop-dup-api) for live display/window frames, and [SendInput](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput) for OS input. DXGI supplies dirty/move regions and cursor metadata that can reduce repeated full-frame processing. Jarvin now uses SendInput for click, wheel and tab/window traversal shortcuts within its foreground-checked Windows worker. Capture still uses Electron desktopCapturer; native Windows.Graphics.Capture and DXGI streaming are future capture adapters.

[UI-TARS Desktop's SDK](https://github.com/bytedance/UI-TARS-desktop/blob/main/docs/sdk.md) documents the screenshot → model action → execute loop used by a visual GUI agent. Jarvin follows that pattern with extra target freshness and foreground-window checks; the new `visual_type` joins a click and typing step in one window. This is an architectural comparison, not an endorsement of that model's accuracy on this laptop. [Windows Agent Arena](https://arxiv.org/abs/2409.08264) provides real Windows tasks and success criteria; its paper reports a large gap between an agent baseline and human performance, so completion must be measured on actual applications. The next acceptance set should cover Chrome, File Explorer, a native settings window and a document editor, including changed focus, popups and multiple displays. The user requested no tests during the current build work, so this acceptance set has not been run.
